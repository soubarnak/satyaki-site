# Research: Python via Pyodide in a Web Worker

Status: research complete, 2026-11-04. Ticket: GitHub issue #31 (map #29).
Unblocks: #42 Decide Ship API and 3D world state model; #44 Decide debugger timeline, playback, and camera model.

## Question

> How should Python run via Pyodide in an isolated Web Worker? Cover: bundle size and first-load cost against the instant-render home map, worker protocol for Ship API calls, line tracing for the debugger, loop guard (500 steps / 3 s), error capture for the kid-friendly translator, and caching/offline options. Recommend versions and loading strategy.

## Recommendation in one paragraph

Run Python in a dedicated module Web Worker hosting self-hosted, exact-pinned Pyodide 314.0.7 (Python 3.14.2, current stable as of 2026-11-04), instantiated lazily when a learner first enters a Python mission — never on the instant-render home map — and kept alive across runs. Put the one TypeScript Ship simulation inside the worker and bind it to Python in `snake_case` as synchronous JavaScript functions (`registerJsModule` / injected globals), so a Ship call is an in-worker function call that appends a `shipDelta` to the current trace step; the main thread only replays trace events into the 3D view. A small Python harness wraps learner code with `sys.settrace` to emit the shared trace stream `{ step, line, kind, locals, shipDelta }` (max 500 events) and enforces the 500-step / 3-second guard from inside, with `setInterruptBuffer` (SharedArrayBuffer, where cross-origin isolation is available) as the mid-run stop and `Worker.terminate()` + respawn as the hard backstop. Self-host the ~6.2 MB (brotli wire) core files same-origin with immutable caching plus a versioned service-worker precache for offline; allow no `micropip` and no learner-triggered package downloads — the stdlib is the whole surface. Fallback: the self-hosted Piston runner (run-to-stdout only, no trace) — with the explicit caveat that Python on Piston is new work, not an existing capability: today's route hard-pins Java 15.0.2 (`lib/server/piston.ts`), ADR-0003 deliberately closes off other languages, and no Python runtime is installed. The second fallback is the pinned jsDelivr CDN URL if self-hosting the Pyodide assets is ever blocked.

## Grounding

Current repo facts (verified by reading the files):

- Next.js 16.4.3, React 19.3.0, TypeScript ^5; no Pyodide, no Three.js, no Monaco, no database, no auth (`package.json`).
- Learner Java today runs server-side on self-hosted Piston on the Coolify family server, internal-only behind a key gateway (`deploy/piston/README.md`, `docs/adr/0002-runner-env-values.md`); the run route pins java 15.0.2, one file, empty stdin, 3000 ms compile / 5000 ms run / 9500 ms abort (`docs/adr/0003-run-route-budget.md`, `lib/server/piston.ts`).
- Outcomes are classified server-side into seven Piston-shaped classes (`ok`, `compile`, `runtime`, `memory-cap`, `time-cap`, `runner-unavailable`, `busy`) and rendered as kid sentences client-side (`docs/adr/0004-run-error-classes.md`, `lib/server/classify.ts`). There is no trace, no world state, no client execution.
- Production image is a `Containerfile` built with podman (never Docker locally), Next standalone output, `public/` copied into the runner image (`Containerfile`, `next.config.ts`). No response headers are configured today — relevant to cross-origin isolation below.

Destination facts that drive the answer (map #29, ticket #30 decision): dual-language Python 3 + Java platform, ages 10–13, instant-render solar-system home map, 3-pane mission cockpit, state-based grader. One TypeScript Ship simulation is the host for both languages (Java `camelCase`, Python `snake_case`); runners emit a trace event stream `{ step, line, kind, locals, shipDelta }`, max 500 events, under a locked 500-step / 3-second guard; the debugger UI is pure replay; Piston stays fallback/CI oracle.

## Version to pin (as of 2026-11-04)

Pyodide's stable channel is **314.0.7** (14 September 2026); the 314.0.0 release (9 June 2026) "Upgraded to Python 3.14.2", so the version number now encodes the Python line ([changelog](https://pyodide.org/en/stable/project/changelog.html)). The npm registry agrees: `pyodide@314.0.7`, MPL-2.0, 14 files, 13,879,282 bytes unpacked ([npm registry record](https://registry.npmjs.org/pyodide/latest), queried 2026-11-04). Pin the exact version in `package.json` and in the asset path (below); a Pyodide upgrade is a Python-minor upgrade, which changes error wording and can move trace semantics, so it must re-run the kid-translator golden tests. Tested browser floor per upstream: Firefox 112, Chrome 112, Safari 16.4 (all 2023) ([Using Pyodide](https://pyodide.org/en/stable/usage/index.html)). One breaking change shapes integration: in 314 "Classic (non-module) workers: No longer supported" because `pyodide.asm.mjs` is an ES module ([changelog](https://pyodide.org/en/stable/project/changelog.html); [web worker docs](https://pyodide.org/en/stable/usage/webworker.html)) — the worker must be created with `{ type: "module" }`.

## Bundle size and first-load cost vs the home map

The full Pyodide distribution is "quite large (200+ megabytes)", but the minimal runtime set (`pyodide-core`, identical to `npm install pyodide`) is what a learner browser needs ([Downloading and deploying](https://pyodide.org/en/stable/usage/downloading-and-deploying.html)). Measured against the official CDN files for v314.0.7 on 2026-11-04 (HEAD probe, brotli wire sizes; a primary artifact, re-runnable):

| File | Wire bytes (br) | Role |
| --- | --- | --- |
| `pyodide.asm.wasm` | 3,438,516 | CPython + statically linked C libraries |
| `python_stdlib.zip` | 2,505,313 | Python standard library |
| `pyodide.asm.mjs` | 262,041 | Emscripten JS half of the runtime |
| `pyodide-lock.json` | 24,708 | Package lockfile (unused if no packages load, still fetched) |
| `pyodide.mjs` | 7,299 | `loadPyodide` loader shim |
| **Total core** | **~6.24 MB** | one-time, cacheable |

File roles per upstream's release-contents table ([Downloading and deploying](https://pyodide.org/en/stable/usage/downloading-and-deploying.html)). Consequences:

- **Never load on the home map.** 6.2 MB plus WASM compile/instantiate would destroy the instant-render requirement. The worker, its TS bundle, and the Pyodide assets must be a lazily imported chunk reached only from Python mission routes (or prefetched at idle after a clear intent signal, e.g. hovering a Python planet — that policy belongs to the cockpit ticket, but the load unit must be separable).
- **Load once, reuse.** Create one worker for the session; `loadPyodide()` runs once at worker start, and each Run reuses the interpreter with a fresh globals dict — `runPython` accepts `globals`/`locals` py-proxies, and upstream documents the custom-namespace pattern for exactly this ([JS API](https://pyodide.org/en/stable/usage/api/js-api.html), [FAQ](https://pyodide.org/en/stable/usage/faq.html)).
- **No packages.** "Only the Python standard library is available after importing Pyodide" ([Loading packages](https://pyodide.org/en/stable/usage/loading-packages.html)); everything else arrives via `pyodide.loadPackage()` or `micropip.install()`. The kid curriculum needs none of it, so first load stays at the 6.2 MB core and runtime stays deterministic and offline-capable. The official worker example calls `loadPackagesFromImports()` per run ([web worker docs](https://pyodide.org/en/stable/usage/webworker.html)) — explicitly do **not** do that for learner code; imports outside an allowlist become a kid-worded error in the harness.
- First-load wall-clock time on school hardware is not derivable from bytes alone (WASM compile dominates on weak CPUs); see Unverified.

## Self-host or CDN?

Upstream offers jsDelivr (`https://cdn.jsdelivr.net/pyodide/v314.0.7/full/`, "Recommended, cached by the browser") and self-hosting ("You will need to serve these files yourself"; any static host with correct WASM MIME type and CORS works) ([Downloading and deploying](https://pyodide.org/en/stable/usage/downloading-and-deploying.html)). Recommendation: **self-host the five core files from the pinned npm package**, served same-origin under a versioned path (e.g. `/pyodide/v314.0.7/`) with `Cache-Control: immutable`. Reasons specific to this product: school networks may filter third-party CDNs (a deployment risk to design against, not a measured fact about any specific school); offline (below) needs same-origin cache control; the site already ships static assets through its own container (`Containerfile` copies `public/`), so the marginal hosting cost is disk in the existing image (13.9 MB unpacked for the whole npm package, [npm registry](https://registry.npmjs.org/pyodide/latest)). Point `loadPyodide({ indexURL })` at that path — `indexURL` is "The URL from which Pyodide will load the main Pyodide runtime and packages", defaulting to the loader's own location ([JS API](https://pyodide.org/en/stable/usage/api/js-api.html)). Keep the pinned CDN URL as a documented fallback only. Container work uses podman, never Docker, per repo rule (`Containerfile` header).

## Worker protocol and the Ship API

Upstream's worker model is message-based: main thread posts `{ id, python, context }`, the worker awaits `loadPyodide()`, builds a Python dict from the context, runs `runPythonAsync`, and posts back `{ result, id }` or `{ error: error.message, id }` ([web worker docs](https://pyodide.org/en/stable/usage/webworker.html)). Workers "cannot directly share globals between a worker and the main thread. In particular, a worker cannot directly manipulate the DOM" (same page) — so the Ship simulation's placement is the one real design decision:

**Place the authoritative Ship simulation inside the worker.** The worker's TS bundle imports the same Ship sim module the Java worker imports (#30). Per run it creates/resets a sim instance from the mission's initial state, then exposes it to Python. The binding mechanism is first-party: `pyodide.registerJsModule(name, jsObject)` makes a JS object importable as a Python module ("Put a collection of functions into a JavaScript object and use `pyodide.registerJsModule()`" — [FAQ](https://pyodide.org/en/stable/usage/faq.html)); injecting via a globals dict built with `pyodide.toPy()` is equivalent ([JS API](https://pyodide.org/en/stable/usage/api/js-api.html)). Python sees the JS functions as `JsProxy` callables and calls them **synchronously**; arguments and results are converted or proxied per the type-translation rules ([Type translations](https://pyodide.org/en/stable/usage/type-conversions.html)). Therefore:

- The Python surface is a thin `snake_case` wrapper object whose methods call the sim's methods 1:1 and, on any state change, record the delta into the harness's "current step" buffer. Sensor reads are ordinary synchronous returns — a loop that reads-then-moves works exactly as in the Java interpreter.
- No `postMessage` per Ship call, no synchronous-RPC-over-`Atomics.wait` machinery, no second sim implementation. The sim contract this imposes (pure TS, no DOM, deterministic, JSON-shaped state/deltas) is handed to #42 below.
- Main thread receives one result message per run: `{ id, status, trace: TraceEvent[], stdout, error? }`. At most 500 trace events makes a single batched `postMessage` fine; streaming chunks are an optimisation #44 can ask for, not a v1 need. The 3D view replays by applying `shipDelta`s to its own sim instance — the same replay contract as Java (#30).
- Stdout is captured in-worker with `pyodide.setStdout({ batched })`; stdin is closed with `pyodide.setStdin({ error: true })` (explicit error handler; the browser default already raises on stdin read, this makes it deliberate) so `input()` fails into the error translator instead of hanging; stderr is captured for diagnostics, not shown raw ([JS API](https://pyodide.org/en/stable/usage/api/js-api.html)).

Rejected placement: sim on the main thread with Python calling it per Ship call. A worker cannot synchronously `postMessage` the main thread; making Python block on a main-thread answer needs SharedArrayBuffer + `Atomics.wait` plumbing on every call, for zero semantic gain over in-worker sim + trace replay.

## Line tracing for the debugger

The harness (our Python prelude, not learner-visible) compiles learner source with a stable filename (e.g. `mission.py`) and installs `sys.settrace`. Per CPython docs, the trace function receives `(frame, event, arg)` with events `'call'`, `'line'`, `'return'`, `'exception'`, `'opcode'`; `'line'` fires when "The interpreter is about to execute a new line of code or re-execute the condition of a loop" ([`sys.settrace`, Python 3.14 docs](https://docs.python.org/3.14/library/sys.html#sys.settrace)). The harness:

- Returns a local trace function only for frames whose filename is the learner file (return `None` for stdlib/sim-internal frames — the documented way to leave a scope untraced, same source).
- On each `'line'` event, first flushes the previous step (line, filtered locals snapshot from the frame, accumulated `shipDelta`, any stdout since) as one trace event of `kind: "line"`, then starts the next step. `'call'`/`'return'`/`'exception'` events can be recorded as their own kinds if #44 wants function-entry markers.
- Snapshots only JSON-safe values (numbers, strings, bools, None, small lists/dicts thereof), stringifying or omitting anything else — the trace must survive `postMessage` structured clone and stay small. The exact locals policy (depth/size caps) is #44's to settle; the mechanism imposes no obstacle.

Two supporting facts: upstream fixed tracing under its async machinery recently — 314.0.6: "`sys.settrace()` and `sys.setprofile()` callbacks are now correctly handled when stack switching" ([changelog](https://pyodide.org/en/stable/project/changelog.html)) — so pin ≥ 314.0.6 (314.0.7 satisfies this). And `sys.monitoring` (added Python 3.12) offers a `LINE` event designed so "a program can be run under a debugger with no overhead if the debugger disables all monitoring except for a few breakpoints" ([`sys.monitoring` docs](https://docs.python.org/3.14/library/sys.monitoring.html)); it is the documented upgrade path if settrace overhead ever matters, but its callbacks do not hand over frame locals as directly, so v1 uses settrace and treats monitoring as future work (see Unverified).

Cost control: tracing fires per learner line, and the guard caps a run at 500 steps, so tracer work is bounded by construction; a single line doing huge internal work (e.g. `sum(range(10**9))`) fires no line events — that hole is covered by the wall-clock layers below, not by the tracer.

## Loop guard: 500 steps / 3 seconds (layered)

1. **Step layer (primary, in harness):** the trace function increments a counter per `'line'` event and raises a harness exception (`StepLimit`) past 500. Raising inside the trace function unwinds learner code into the harness's `except`, which finalises the trace and reports `step-limit`. Note the documented semantics: loop-condition re-execution counts as a line event ([`sys.settrace`](https://docs.python.org/3.14/library/sys.html#sys.settrace)) — #44 should adopt "one line event = one step" as the shared definition so Python and Cadet Java count alike.
2. **Wall-clock layer (in harness):** every N line events, compare elapsed time to 3 s and raise `TimeLimit` similarly. Cheap because step 1 already bounds event count.
3. **Interrupt layer (main → worker):** `pyodide.setInterruptBuffer()` with a `SharedArrayBuffer`; the main thread writes `2` (SIGINT) and "By default, when the interrupt fires, a `KeyboardInterrupt` is raised" ([Interrupting execution](https://pyodide.org/en/stable/usage/keyboard-interrupts.html); [JS API](https://pyodide.org/en/stable/usage/api/js-api.html)). This reaches "Python code and also of C code that allows itself to be interrupted by periodically calling `PyErr_CheckSignals()`" (same page), covering the no-line-event hole for bytecode loops. It requires Pyodide in a web worker (satisfied) and SharedArrayBuffer, which requires the document to be cross-origin isolated — secure context plus COOP/COEP headers ([MDN SharedArrayBuffer](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer)). The repo configures no headers today (`next.config.ts`), so enabling this layer means adding COOP/COEP to the app (Next headers or the Coolify proxy) and feature-detecting `crossOriginIsolated`; where unavailable, degrade to layer 4 alone.
4. **Terminate layer (backstop):** main thread enforces an outer deadline (the 3 s budget plus a small grace for interrupt handling); on expiry it calls `Worker.terminate()`, which "immediately terminates the Worker … it is stopped at once" ([MDN Worker.terminate](https://developer.mozilla.org/en-US/docs/Web/API/Worker/terminate)), then respawns the worker for the next run. This layer cannot be starved by learner code, including code that tampers with `sys.settrace` — a real consideration, since tracing is a debugging mechanism, not a sandbox (CPython makes the analogous warning for audit hooks: not "suitable for implementing a 'sandbox'" — [`sys.addaudithook`](https://docs.python.org/3.14/library/sys.html#sys.addaudithook)). The user-visible cost of a terminate is one Pyodide reload from cache before the next run; the kid-facing message is the same `time-cap` sentence. Respawn cost is why layers 1–3 exist.

## Error capture for the kid-friendly translator

Two channels, prefer the structured one:

- **In-Python (primary):** the harness runs learner code in `try/except` and, on failure, extracts `{ excType, message, line, filename }` from the traceback's learner-file frame and returns it as data. This follows upstream's own guidance: `PythonError` "contains no reference to the Python exception that caused it. You can find the actual Python exception … as `sys.last_exc`" and "The easiest way is to only handle the exception in Python" to avoid leaking stack frames via proxies ([JS API, `pyodide.ffi.PythonError`](https://pyodide.org/en/stable/usage/api/js-api.html)).
- **In-JS (backstop):** anything escaping the harness arrives as a thrown `PythonError` whose `.type` is "The name of the Python error class, e.g, RuntimeError or KeyError" and whose message carries the formatted traceback (same source). Because the harness compiles with a real filename, tracebacks show source lines: `runPython`'s `filename` option gives tracebacks that "will show source lines (unless the given file name starts with < and ends with >)" ([JS API](https://pyodide.org/en/stable/usage/api/js-api.html)) — the `File "mission.py", line N` shape is parseable as a last resort.

The translator then maps `(excType, line)` → one kid sentence + line number, in one shared TS module used by both language workers (extending the ADR-0004 idea — classify once, render sentence + raw detail — from Piston classes to a runner-owned taxonomy, per #30's implications). Note the boundary change this implies: ADR-0004 mandates server-side classification ("client never classifies", `lib/server/classify.ts`), while in-worker Python error capture is client-side by construction — so client runs need a short ADR superseding ADR-0004 for the browser runners when this lands, exactly as #30 flagged for Cadet Java. Guard outcomes (`step-limit`, `time-cap`, interrupt, worker-terminated) are first-class classes in that taxonomy, keeping infrastructure failure visually distinct from a child's mistake (the ADR-0004 principle, `lib/server/classify.ts`). `SyntaxError`/`IndentationError` arrive through the same path at harness compile time with their line attached by the traceback. Translator patterns must key on exception type and line, not on CPython message text, which changes across Python versions (see Unverified).

## Caching and offline

- **HTTP cache:** versioned same-origin paths + immutable cache headers make repeat visits fetch zero Pyodide bytes; the worker JS chunk is cached like any Next static asset.
- **Service worker (cache only):** precache the five core files + worker chunk into a versioned Cache Storage bucket (`pyodide-314.0.7`) on first Python-mission entry — the standard Cache API pattern, not a Pyodide feature ([MDN Cache](https://developer.mozilla.org/en-US/docs/Web/API/Cache)) — so Python levels then run fully offline and survive HTTP-cache eviction better. Do not run Pyodide *inside* the service worker: upstream documents that as a separate pattern (for fetch interception) with a dynamic-import workaround — service workers "forbid dynamic `import()`", requiring `createPyodideModule` to be passed manually ([service worker docs](https://pyodide.org/en/stable/usage/service-worker.html)). Service worker = cache layer; web worker = execution layer. Service workers require https or localhost (same source); the production site is https (`deploy/piston/README.md`).
- **No runtime package downloads** means no PyPI dependency and nothing else to cache. If a future level truly needs a package: install once with `micropip`, call `micropip.freeze()` to "Produce a json string which can be used as the contents of the pyodide-lock.json lock file", self-host that lockfile + wheels, and load via `loadPyodide({ lockFileURL })` + `loadPackage()` — "much faster and you will always get consistent versions" ([micropip API](https://micropip.pyodide.org/en/stable/project/api.html); `lockFileURL` in [JS API](https://pyodide.org/en/stable/usage/api/js-api.html)). Note `packageCacheDir` is Node-only, "ignored in browsers" ([JS API](https://pyodide.org/en/stable/usage/api/js-api.html)) — there is no built-in browser package cache to lean on, another reason the stdlib-only stance matters.
- Offline scope honesty: after precache, *Python execution* is offline. Accounts/progress sync remain online features with the localStorage fallback already locked by the map; the worker design neither helps nor harms that.

## Unverified — do not plan against as facts

- First-load wall-clock time (download + WASM compile + stdlib import) on school hardware/Chromebooks. Only wire bytes were measured (2026-11-04, this network); a device spike must produce the number before any "loads in Xs" claim.
- `sys.settrace` overhead multiplier under Pyodide/WASM and the cost of locals snapshots. Bounded by the 500-step cap, but not measured.
- `sys.monitoring` as a drop-in, locals-capable replacement for settrace in this harness. The API and `LINE` event exist (Python 3.12+); a working locals-snapshot design on it is unproven here.
- COOP/COEP cross-origin isolation on the live Coolify deployment: no headers are configured anywhere today (`next.config.ts`), so `setInterruptBuffer`/SharedArrayBuffer is available nowhere in v1 until headers ship and are verified on Coolify — the v1 guard is therefore layers 1, 2 and 4 (settrace step/wall-clock + terminate/respawn) only. Interaction with future auth, embeds, or analytics is additionally unspiked. The design must work (degraded) without it.
- Safari's SharedArrayBuffer/`Atomics.wait` behaviour in module workers. Feature-detect; assume layer-4-only until proven.
- Uncompressed per-file sizes: the CDN probe returned brotli-encoded lengths only; the npm package's 13,879,282-byte unpacked total is an upper bound for the file set, not a per-file breakdown.
- Python 3.14 exception message wording as translator input. Exception *types* and traceback line numbers are the stable interface; any message-text pattern is a guess until goldened by tests.
- Service-worker Cache Storage quota/eviction behaviour on managed school devices; offline is best-effort, not guaranteed storage.
- Any claim that learner code cannot escape the in-harness guard layers (it can try: `sys.settrace(None)`, C-level loops). Containment rests on the worker boundary + terminate layer + browser sandbox, and on the sim exposing only Ship functions — a threat-model review belongs to implementation, not this ticket.

## Implications for downstream tickets

**#42 (Ship API and 3D world state model)** receives: the sim must be a pure, DOM-free, deterministic TypeScript module instantiable inside a worker, with `reset(initialState)`, synchronous methods taking/returning JSON-shaped values, and every mutating call producing a serialisable delta; a second instance on the main thread must be able to reconstruct any point by replaying deltas. The Python surface is a generated/derived `snake_case` binding over the same methods (registered via `registerJsModule` or globals injection) — #42 owns the name-mapping table and which calls count as deltas vs pure sensor reads. #42 still owns: the actual Ship vocabulary, world-state shape, and grader state comparisons.

**#44 (debugger timeline, playback, camera)** receives: the trace contract is producible from Python exactly as from Cadet Java — one event per executed learner line (`kind: "line"`, loop-condition re-runs included), plus optional call/return/exception kinds, each with `line`, filtered `locals`, and the `shipDelta` accumulated on that line; max 500 events, delivered as one batched result per run; playback is pure replay. #44 still owns: locals snapshot policy (which values, depth/size caps), whether call/return events are steps, scrub/redraw semantics, camera model, and the respawn-after-terminate UX copy. The shared step definition ("one line event = one step", 500-step / 3 s guard) should be ratified there so both languages count identically.

Both: Pyodide/Python upgrades are versioned events (314.0.7 = Python 3.14.2) that must re-run translator and trace goldens; Piston can serve as a Python oracle in CI the same way #30 uses it for Java only after a Python runtime is installed on the Piston service and ADR-0003's Java-only pin is amended — that is a small project of its own, not a switch to flip (current route: `lib/server/piston.ts`).
